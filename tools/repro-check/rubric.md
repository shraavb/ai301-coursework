# Rubric: is this reproduction package ready to post?

## Checks

| Check | Evidence | Pass condition | Weight |
|---|---|---|---|
| env-recorded | The repro report's environment record (OS, language/tool version, install method, and any config the behavior depends on), read against the target named in the issue and the repo-facts block (latest release). | The report names at least the versions or build that make the result placeable (for example the release or commit of the tool plus the OS), AND any difference from the version the issue reports is stated in the report. No environment record at all fails, even if everything else is good. | required |
| steps-followable | The repro report's steps/commands, read as a stranger starting from a clean machine. | A stranger could re-run the trigger from what is written: the exact commands or inputs are shown, the starting state is given or obvious, and nothing needed lives only in a private repo, private file or unshared config. A terse list that is complete passes; a long polished one that skips the trigger fails. | required |
| behavior-matches-issue | The output excerpts, logs or screenshots in the repro report, read against the exact error, output or crash the issue describes, and the trigger (input, syntax, version, config) the issue names. | If the report says it reproduced: the artifact shows the same behavior the issue describes (same error text, exit status, crash vs graceful error, same input shape). If the report says it did NOT reproduce: the attempt used the issue's own trigger (same input shape or syntax, a version or setup it names, deviations acknowledged) and the real output is shown, so the non-reproduction is a fair test. Fail if the artifact shows an adjacent symptom, runs a modified input or syntax, tests a different version without saying so, shows only that the tool runs, or an attempt that does not use the issue's trigger. | required |
| outcome-honest | The report's stated result (reproduced, not reproduced, partial) read against its artifacts. | What the report claims is shown by what it attaches. An evidenced "could not reproduce" (real attempt, artifacts, named differences) passes. Fail if it asserts reproduction, a root cause, or "verified" with no artifact, or states a result its own artifact contradicts. | required |
| claim-specific-honest | The claim comment, read against the issue text. | The claim names this issue's specifics (the symptom, function, command or file), says what the author will do next (investigate, test, report back), and promises at most investigation. Fail if it is interchangeable boilerplate ("assign me"), a bare +1, promises a guaranteed fix or a date, or states reproduction with no report behind it. | required |
| repo-conventions | The repo-facts block: bug-report template asks and the contribution policy (including any AI policy), read against both comments. | Both comments respect the stated policy. If the policy requires disclosure of AI assistance, the comments disclose it (tool and extent). If it requires comments in the author's own words, they read as human-written. If it fully bans AI contributions, fail. No stated AI policy or a permissive one passes. Treat the author as AI-assisted in this course. | required |
| control-or-contrast | The report's control run or comparison (a working variant, an older version, the issue's own trigger note). | The report includes a control or contrast that shows the failure is tied to the trigger. | preferred |
| expected-vs-actual | The report's closing statement. | States expected and actual behavior as observations, matching the artifacts. | preferred |

## Verdict rule

Accept (ready to post) if and only if every required check passes. Any required fail means reject. A required check graded unclear counts as fail. Preferred checks never change the verdict. Judge the thing itself, never the formatting or length: a terse complete report can be accepted and a long polished one can be rejected.
